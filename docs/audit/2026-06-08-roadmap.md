## The point of all of it
The business goal is **a ranked shortlist of law-firm acquisition/deal targets**, not a clean
directory for its own sake. Everything below is ordered by what it takes to get from today's raw
source records to a **scored, explainable shortlist an analyst can act on.** The audit's headline
gap (P3) is that this final layer doesn't exist yet and the canonical record can't feed it — so the
roadmap ends there deliberately.

## §1 — Where we are
- **417,726 source records** (martindale 81%, justia 10%, az_bar 7%, findlaw 2%); ~27k website
  crawls (20.7k verified). Canonical `firms` not yet built.
- **~60% of records are nameless** (justia 100%, martindale 57.6%); `primary_city/state` NULL on
  **100%**; the 81% martindale majority has 0% website / 4.4% phone. → the corpus is **not yet
  resolution-ready**; data-readiness (Phase 1) gates a meaningful run.
- **Built & validated:** ingestion (national, crash-safe), the hand-rolled resolver
  (blocking→scoring→fusion, dry-run-validated, zero false merges), the website crawl.
- **Decided:** website becomes `source="website"` in `firm_source_records` (MDM shape); **Postgres
  DEFERRED** (not necessary; $0 constraint); **Splink runs on DuckDB** (no migration).

## §3 — Phases in detail

### Phase 0 — Foundations (now, parallel, unblocked)
- **Eval harness (P1) — the keystone.** [Canonizer] A stratified-by-score, clerically-labelled
  candidate-pair set (seed from the known-firm oracle: Snell & Wilmer, Morgan & Morgan, the
  multi-domain + toll-free-lead-gen cases), scored with **Splink's native
  `evaluation.accuracy_analysis_from_labels_table`** (precision/recall/F1/ROC across thresholds) +
  cluster metrics (B-cubed). Idiomatic ER practice: sample the *ambiguous middle*, not the obvious
  0/1 pairs; over-sample cross-source pairs. **This is engine-agnostic and gates every matcher
  decision** — build it first.
- **Deal-target rubric design (P3, v0).** [Alex + Cleanser] Lock the "what is a good target"
  criteria now (decisions Q-strategy / Q-signals), even before firms exist, so Phase 4 is mechanical.
- **CI (C2)** [Cleanser, on Mastermind lane-ack] + **`db.py` `synchronous=NORMAL` (C4)** + **drop
  `click` (C5)** [Mastermind] + **README (C1)** [Cleanser]. Quality floor for a 5-agent repo.

### Phase 1 — Data readiness (Mastermind, queued; gates a real run)
Run order (Mastermind's plan; the data-quality audit quantifies the payoff):
1. **martindale firm-profile `enrich`** → names/websites/phones for the 57.6% nameless martindale.
2. **office-parser fix** → recovers `primary_state` for **76,579** martindale rows.

→ Output: a **named, geo-located, website-enriched** corpus that is actually resolvable.

### Phase 2 — Matcher (Canonizer; decision gate)
- **Splink-on-DuckDB pilot** per `splink-adoption-plan.md`: `ATTACH` the SQLite file, EM-train m/u
  weights, cluster. Judge against the Phase-0 eval set + oracle **vs** the current floors/caps.
- **Decision (Q-matcher):** adopt Splink iff it ≥ the bespoke matcher on the metric. Either way the
  matcher becomes *measured*, and the growing floors/caps stack stops being the maintenance surface.
- **Robust headcount (OPEN ITEM 1)** [Canonizer, independent of matcher] — replace `max()` with
  union-floor + corroboration gate (scope/office_count/cluster-size) + median/trimmed-mean once
  multiple estimates exist. (The lead-gen TF-weighting falls out of Splink for free.)
- **Multi-domain (OPEN ITEM 2)** — Splink's name+phone+geo comparisons cluster these without a
  special pass; verify on the oracle (Thompson & Hiller, Dickinson Wright).

### Phase 3 — Canonical record widening (Mastermind schema + Canonizer apply)
- Promote the deal-signals onto canonical `Firm` (scope, office_count, practice-area roll-up,
  notable_signals, a size band) **and populate the existing-but-empty `offices` / `firm_persons` /
  `firm_practice_areas` tables at survivorship**; add the `firms.phones` union the fusion design
  already calls for. **One migration, folded with the website-as-source landing** (do it once).
→ Output: golden records that actually carry the signals Phase 4 scores.

### Phase 4 — Deal-target scoring (the payoff; owner to assign)
- A **transparent, explainable weighted rubric** (not an opaque model) over the **observable
  proxies** → a ranked, tiered shortlist with score components stored (mirroring
  `match_review_queue`'s auditable `score_components`). Implement as a `firms_scored` SQL view or a
  small `scripts/rank_targets.py`; version the rubric in `assumptions.md`.
- **Be honest about the ceiling:** we can observe **headcount, practice mix, scope/geography,
  office_count, firm age, website marketing-intensity, active/closed** — i.e. *roll-up screening
  signals*. We **cannot** observe revenue, revenue-per-lawyer, margin, growth, realization/collection,
  client concentration (no financials). So the output is a **prioritized outreach/diligence list**,
  not a valuation — financials enter in diligence.
- Weights are set by the **target strategy** (Q-strategy): a PE-style **roll-up** weights
  consumer/marketing-driven practices (PI, family), small-mid size, multi-geography, marketing
  intensity; a **platform/tuck-in** strategy weights larger, established, multi-office firms. This is
  why the rubric needs your thesis (§7).

### Phase 5 — Run + iterate (post-Martindale)
- Full `resolve → apply → score` on the complete corpus; re-run the data-quality + eval audits;
  tune thresholds/rubric. Mid-scrape runs are fine (idempotent) but **provisional**; the
  authoritative run is after Martindale completes.

## §4 — Idiomatic notes (researched)
- **Matcher → Splink (DuckDB).** Fellegi-Sunter + **unsupervised EM**; DuckDB handles our 417k in
  ~1 min and **reads the SQLite file directly** (`ATTACH … (TYPE sqlite)`) → no migration, $0.
  Splink's PG backend is "new/untested" → stay on DuckDB regardless of any future store change.
- **Eval → Splink-native + standard ER metrics.** `accuracy_analysis_from_labels_table` for
  precision/recall/F1/ROC across thresholds; B-cubed/pairwise-F1 for clusters. Build the label set by
  **stratified clerical review of the ambiguous score band** (matches are <1% of pairs, so don't
  random-sample raw pairs; sample within blocked candidates).
- **Robust headcount → robust statistics.** Union = hard floor; median / trimmed-mean / MAD-based
  outlier rejection once ≥2 estimates exist — never `max()` (0% breakdown point).
- **Deal-target layer → transparent rubric, not ML.** Explainability + stored components matter for
  an investment workflow; mirror the existing `score_components` pattern. Grounded in PE law-firm
  roll-up criteria (consumer/marketing-driven, size, geography, growth) restricted to observable
  proxies.
- **Datastore → SQLite (operational) + DuckDB (Splink compute).** Defer Postgres until a real
  trigger (sustained same-row concurrent writes / multi-host / heavy JSONB analytics); a free *local*
  PG covers those, no cloud spend.
- **Tooling → uv + ruff + GitHub Actions** (`astral-sh/setup-uv` → `ruff` + `pytest`); the suite is
  4.5s, so CI is near-free insurance for a 5-agent shared `main`.
